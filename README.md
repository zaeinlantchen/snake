# 基于 LVGL 8.3 的多人联机贪吃蛇游戏 — 项目文档

> 项目代号 `LunaUI`（客户端）/ `snake_server`（服务端）
> 目标平台：Samsung S5P6818 开发板（Cortex-A53 八核 1.4GHz，Mali-400），Linux 3.4.39，800×480 FrameBuffer
> 技术栈：LVGL v8.3 + C / C-S 架构 + 纯二进制 TCP 协议（cJSON 已弃用，保留文件）

---

## 一、设计目标

本项目以“在嵌入式开发板上实现一款**可多人联机**的贪吃蛇游戏”为总目标，把一款经典的纯单机小游戏升级为**随开随玩、人人可加入**的实时对战游戏，并借助 LVGL 在受限的嵌入式硬件上提供一套完整、流畅的图形界面。

具体拆解为以下目标：

| 目标 | 说明 |
| --- | --- |
| **多人联机** | 多台开发板连到同一台服务端，同房间实时竞技、实时看到彼此、实时排名 |
| **权威逻辑** | 服务端持有全部游戏逻辑（移动/吃食/碰撞/得分/胜负），客户端只渲染，杜绝作弊与不一致 |
| **实时流畅** | 网络运行于局域网且帧率固定（10Hz），客户端通过插值渲染提升到视觉 ~30fps |
| **两种地图玩法** | 经典（撞墙即死）与环形（穿墙、8 方向）两种地图，兼顾传统玩家与多变玩法 |
| **清晰的前后端分层** | 界面（page）、网络（net）、数据模型（snake）三模块解耦，可独立修改与复用 |
| **嵌入式适配** | 800×480 屏幕、32 位色深、交叉编译工具链、中文界面（FreeType 中文字体） |

## 二、功能描述

### 2.1 界面流程

```
用户名屏  →  输入昵称 + Start（自动连接服务器 192.168.46.133:5000）
   ↓
主菜单    →  左侧：经典/环形地图选择  |  右侧：单人模式 / 多人模式
   ↓
多人模式  →  房间选择屏（房间列表 / 按房间号加入 / 随机加入 / 创建房间 / 返回）
   ↓
游戏屏    →  顶部得分/名次/无敌 + 右上“退出” + 左侧虚拟摇杆(环形)/方向键(经典) + 棋盘
```

- 用户名屏：输入昵称，点 **Start** 连接服务器；输入框聚焦弹出底部软键盘，失焦隐藏；底部显示连接状态/错误信息。
- 主菜单：可切换地图（经典/环形），并选择**单人模式**或**多人模式**。
- 房间屏：单人模式由服务器直接开一间专属房；多人模式可**创建房间 / 按房间号搜索加入**，或点击房间列表直接进入。
- 游戏屏：顶部菜单栏实时显示本机昵称、得分、名次、食物进度、无敌剩余秒数与地图类型；右上角退出回主菜单。

### 2.2 游戏规则

| 规则项 | 经典地图（40×24） | 环形地图（80×48） |
| --- | --- | --- |
| 地图尺寸 | 40×24，地图即屏幕 | 80×48，远大于屏幕，蛇头居中相机滚动 |
| 移动模型 | 格点移动，每帧前进 1 格 | 像素级连续移动，蛇头每帧前进 20px（10Hz） |
| 方向 | 仅上下左右 4 向 | 8 向（4 基本 + 4 对角线） |
| 边界 | 撞墙即死 | 越界从对侧穿出 |
| 小食物 | 不铺 | 整图随机稀疏分布（目标 960 个），定期刷新 |
| 大食物 | 定时生成 | 定时生成 |
| 自身碰撞 | 判死 | 不判死 |
| 技能 | 无 | 加速 / 护盾（吃食物获得） |
| 出生 | 出生即带 8s 无敌 | 出生即带 8s 无敌 |

其他规则细节：

- **出生无敌**：蛇随机出生在地图任意位置，带 **8 秒无敌**（80 帧 × 100ms）；无敌期间不死、可穿过其它蛇（其它蛇也不因此受伤），无敌期撞墙原地不动；顶部显示 `Invincible: Ns` 倒计时，无敌蛇带白色描边。
- **加长与得分**：小食物 +1 分、大食物 +10 分；每累计吃 10 个小食物长度 +1，吃 1 个大食物直接 +1。
- **技能（仅环形地图）**：
  - **加速**：每吃 3 个大食物获得 1 次，激活后每帧前进 40px（5s 生效）。
  - **护盾**：每吃 40 个小食物获得 1 次，激活后等同无敌（5s 生效）。
  - 每个技能最多同时持有 1 个，须未持有且未激活才能获得；使用且效果结束后才能再次获得。
- **胜负**：多人时存活蛇 ≤ 1 即结束；单人时蛇死亡即结束。结束广播 `over`（含胜者 id，-1 为平局/无人存活），倒计时 3s 后自动开启新一局并广播 `round`。
- **名次**：按得分排序，得分高者名次靠前。

### 2.3 交互控制

- **环形地图**：左下虚拟摇杆（与手机摇杆布局一致，浮于游戏区上），拖动按 8 个扇区判定方向，松开保持原方向；右侧技能栏（加速/护盾）点击使用。
- **经典地图**：左下 4 方向按键（D-pad）。
- **退出**：游戏屏右上退出键，离开房间回主菜单。
- 界面文字全部英文/中文区分为：内置 Montserrat 字体只含 ASCII，中文文案经由 FreeType 加载外部字库渲染。

## 三、设计方案

### 3.1 总体架构：C/S（客户端/服务端）与“服务端权威”

采用经典的**客户端/服务端**架构，且采用**权威服务端**模型：

- **服务端**占用极少资源、持有全部游戏逻辑，是唯一的世界状态权威；客户端只是“观察者 + 输入源”。
- 客户端每帧只做两件事：`渲染服务端下发的世界状态` 与 `把玩家输入（方向/技能/房间操作）发给服务端`。

```
                     ┌─────────────────────────────┐
                     │   server/  （Linux，权威端）  │
                     │   房间管理·移动·碰撞·吃食·技能  │
                     └──────────────┬──────────────┘
                        纯二进制帧协议（TCP, 大端）
                     ┌──────────────▼──────────────┐
                     │ 客户端 zaeinGui/LunaUI/S5P6818│
                     │  page(界面) net(网络) snake(模型) │
                     └─────────────────────────────┘
```

**为什么不用本地推进（客户端也跑逻辑）？** 多人实时对战对“一致性”要求极高，若每个客户端各跑一份逻辑，会出现“我看到的和你看到的不一样”“我明明没死却被判死”等问题。权威服务端可彻底避免分歧，同时天然反作弊、便于回放与调试。

### 3.2 通信协议设计

协议经历了一次从 **JSON 文本** 到 **纯二进制帧** 的重大演进（git 记录：`新增了地图玩法，将原有的json数据流改为了纯二进制数据流`）。最终采用**纯二进制帧**：

```
┌────────────┬───────────────┬──────────────────────────────┐
│ type 1B    │ plen 2B (大端) │ payload 0~16384B             │
└────────────┴───────────────┴──────────────────────────────┘
  帧头 PROTO_HEADER_LEN = 3 字节
```

设计要点：

- **定界**：3 字节帧头（类型 + 负载长度），无分隔符、无转义；长度不含帧头。
- **字节序**：多字节整数一律**大端**，两端共用同一套 `pr_put_u16/u32` `pr_get_u16/u32`。
- **半包/粘包**：TCP 是字节流，接收端用累积缓冲 + 循环切帧处理（`acclen`/`rbuf`）。
- **组解对称**：`tick → 小食 → 大食 → 技能道具 → 蛇` 的组包顺序与解析顺序严格一一对应，每步做 `remain` 越界保护。
- **非法帧防护**：长度超上限即丢弃整个缓冲。

消息全集（详见 `server/inc/protocol.h` 与客户端副本）：

| 方向 | 消息 | 负载 |
| --- | --- | --- |
| C→S | `MSG_JOIN(1)` | name[16] |
| C→S | `MSG_MODE(2)` | mode u8, wrap u8 |
| C→S | `MSG_ROOM_LIST(3)` | — |
| C→S | `MSG_CREATE_ROOM(4)` | wrap u8 |
| C→S | `MSG_JOIN_ROOM(5)` | room u32 |
| C→S | `MSG_RANDOM_JOIN(6)` | — |
| C→S | `MSG_DIR(7)` | dir u8（0..7，禁止 180° 反转） |
| C→S | `MSG_LEAVE(8)` / `MSG_BYE(9)` | — |
| C→S | `MSG_USE_SKILL(10)` | skill u8 |
| S→C | `MSG_WELCOME(20)` | id u32, cols u16, rows u16 |
| S→C | `MSG_ROOMS(21)` | n u8 + n×(id u32, players u8, max u8, wrap u8) |
| S→C | `MSG_ROOM(22)` | room u32, mode u8, wrap u8, cols u16, rows u16 |
| S→C | `MSG_STATE(23)` | 世界快照（见 3.3） |
| S→C | `MSG_OVER(24)` | winner i32 |
| S→C | `MSG_ROUND(25)` | — |
| S→C | `MSG_ERROR(26)` | 错误字符串 |

### 3.3 世界状态帧（STATE）与“连续移动模型”

这是本项目最核心的设计演进点（阶段 C：**连续移动模型**）。早期用“格点坐标”（每格一个坐标）表示蛇身，但画面生硬、无法体现平滑。最终改为**像素级连续轨迹折线**：

- **蛇头**：每帧（`TICK_MS=100ms`）沿当前方向前进 `SNAKE_SPEED_PX=20px`（10Hz × 20px = 200px/s）；加速技能时翻倍为 40px。
- **身体**：`path[]` 保存蛇头走过的折线轨迹，`path[0]=蛇头`，越往后越靠尾；身体 = 最近 `min(len, path_n)` 个点，相邻点沿路径间距约 20px。
- **环形跨边**：蛇头跨地图边界时，服务端按 2px 子步自动插入“边界前后”两个点，保证相邻折线点距离恒 ≤ 20px、坐标已包装（0..cols\*20-1）。因此**客户端逐段连线即可正确渲染，无需自己补跨边点**。
- **经典地图**：仍为格链 `gbody[]`，每格唯一，撞墙即死。

`MSG_STATE` 负载布局（全部大端）：

```
tick u32
small_n u16          小食数量
small_n × {px u16, py u16}    小食左上角像素坐标(4×4)
big_n u8             大食数量
big_n × {px u16, py u16}      大食左上角像素坐标(16×16)
pickup_n u8          技能道具数（保留字段，恒 0：技能改为吃食物获得）
nsnakes u8
nsnakes × {
    id u32, color u8, len u16, score u16, inv u8, small_eaten u8,
    skills u8, speed_ticks u8, shield_ticks u8, name[16],
    body[ len × {x u16, y u16} ]   像素折线，body[0]=蛇头
}
```

### 3.4 客户端渲染方案

客户端不自己推进游戏，只渲染服务端快照。为在“10Hz 状态”下获得流畅观感，采用了**插值渲染 + 相机**：

- **两帧快照 + 逐点插值**：保存 `prev`/`cur` 两帧，`draw_board()` 由 33ms 定时器多次重绘，插值系数 `k∈[0,1]`，`k=0` 画上一帧、`k=1` 画本帧，位移单调向前，蛇身平滑滑动（30fps）。蛇身点数跳变的帧（吃食变长/重生）改为**直画本帧**，避免视觉塌陷。
- **经典地图**：相机固定在原点，地图即屏幕（40×24），蛇身为方块。
- **环形地图**：相机跟随“插值后的本机蛇头”，蛇头固定在屏幕中心、地图滚动；只绘制视口内的实体，并处理“跨缝合线”跳段（`seg_straddle`）与“最近映像”（`wrap_off`，让蛇身还能从屏幕对侧出现）。
- **棋盘**：用 `lv_canvas` 800×480 缓冲绘制背景底、随相机偏移的网格线、食物（4×4 红 / 16×16 金）、所有蛇（圆头粗线 + 拐角补圆点，蛇头更亮更大，无敌/护盾白描边）。
- **技能栏**：三态（灰暗不可用 / 绿框已持有 / 金框放大激活中）。

### 3.5 线程与并发模型

客户端采用**单 LVGL 主线程 + 一条网络后台线程**：

- **网络线程**：负责建立连接（带超时、非阻塞 connect + select）并持续 `recv`；把切好的完整帧放入**线程安全消息队列**（深度 8，满时丢弃最旧帧），**绝不在网络线程调用任何 LVGL API**。
- **主线程**：`lv_timer_create(poll_timer, 30ms)` 周期 `net_poll_msg()` 取帧、`net_send_msg()` 发命令。
- 状态与队列分别以 `pthread_mutex` 保护（`g_state_lock` / `g_queue_lock`）。

服务端采用**单进程 select 事件循环 + 非阻塞收发**：`select` 同时监听监听 socket 读写与每个客户端 socket，超时自动对齐 100ms 帧周期；每客户端一个输出缓冲 `obuf`，可写时 `out_flush`。

### 4.2 客户端模块划分

| 模块 | 职责 | 关键接口 |
| --- | --- | --- |
| **page**（界面） | 仅负责界面布局与输入采集，通过回调向上层解耦 | `ui_*_screen_create(..., cb_*)`、`ui_game_update()` |
| **net**（网络） | TCP 连接 + 后台线程 + 线程安全队列 | `net_init/connect/close/send_msg/poll_msg/state` |
| **snake**（模型） | 蛇/食物/世界数据结构，解析 STATE 帧 | `snake_world_init/reset_round/parse_state` |
| **snakeInit**（协调器） | 把三者串起来：屏幕切换、消息分发、发 JOIN/DIR/MODE、处理 WELCOME/ROOMS/ROOM/STATE/OVER/ROUND/ERROR | `snakeInit()` |

**依赖方向**：`snakeInit` → `page` / `net` / `snake`；`page` → `snake`（只读世界状态）；`net` ↔ 协议；`snake` → 协议。`page` 不依赖 `net`，`net` 不依赖 `page`，二者通过 `snakeInit` 回调与消息分发连接。

### 4.3 服务端数据结构

- `client_t`（max 32）：fd、全局唯一 id、昵称、模式、所在房间、接收缓冲 `rbuf`、发送缓冲 `obuf`。
- `room_t`（max 8）：房间号、模式（单人/多人）、地图类型 wrap、地图尺寸、食物数组、玩家数组、刷新/生成倒计时、回合状态（`round_started` / `restart_ticks`）。
- `player_t`（每房 max 8）：client_id、昵称、颜色（=房间槽位 0..7）、存活、得分、无敌 ticks、小食/技能进度、逻辑长度、方向、蛇头位置、轨迹折线 `path[]`、经典格链 `gbody[]`、技能持有/效果字段。

### 4.4 数据流（时序）

```
[客户端 UI]                           [服务端]
  输入昵称 → send_join()  ──帧──▶  handle_join 存昵称 → 回 WELCOME
  选模式   → send_mode()  ──▶     handle_mode 建房/列房 → 回 ROOM / ROOMS
  摇杆方向 → send_dir()   ──▶     handle_dir 写 ndir
                                    ↓ 每 100ms
                                advance_tick() 推进 + broadcast_state()
                              ──MSG_STATE──▶  主线程取帧 → parse_state
                                              → ui_game_update → draw_board(插值)
  点技能   → send_skill() ──▶     handle_use_skill 激活效果
  退出     → send_leave() ──▶     client_leave_room 回收空房 → 回主菜单
```

## 五、实现过程

项目经历了从“单机 demo”到“多人联机 + 双地图 + 技能 + 平滑渲染”的多轮演进。结合 git 提交记录与实际代码，可归纳为以下几个阶段：

**阶段一：基础框架与联机雏形（JSON 协议）**
- 搭建 LVGL 客户端（fbdev + evdev），实现用户名屏、主菜单、基础棋盘；服务端用 TCP + **JSON**（cJSON）实现连接与消息转发。
- 完成“输入昵称 → 连接 → 单人可玩”的最小闭环。
- 关键修复：服务端 `room_reset` 曾把玩家槽位 `client_id` 用 `memset` 清成 0（应为 -1），导致“幽灵玩家”、玩家无法真正入房、不广播 state 等 bug（提交：`修复服务端关键 bug`）。

**阶段二：纯二进制协议与双地图**
- 将 JSON 数据流整体替换为**纯二进制帧**（帧头 3 字节 + 负载），提升带宽效率与解析性能（提交：`将原有的json数据流改为了纯二进制数据流`）。

**阶段三：连续移动模型与平滑渲染**
- 把蛇身坐标从“格点坐标”升级为“**物理/像素坐标**”，采用连续移动模型 + 轨迹折线，优化蛇身形态使其更圆润，并提供**插值渲染**使两帧之间过渡平滑（提交：`将坐标从格点坐标改为物理坐标`、`优化了渲染逻辑，提供了插值渲染`）。

**阶段五：打磨与完善**

**平台与编译实现**
- 客户端：`arm-linux-gcc` 交叉编译，`Makefile` 通过 `find LunaUI -name "*.c"` 自动收集源文件，链接 FreeType、pthread、math；生成 ARM 版 `zaeinGUI` 拷贝到板子运行。
- 服务端：`gcc`（或 `arm-linux-gcc` 交叉）编译 `src/server.c + lib/cJSON.c`，生成 `bin/snake_server`，默认端口 5000。
